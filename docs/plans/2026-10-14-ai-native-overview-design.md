# AI Native 概览文章设计

## 目标

第一篇文章回答 AI Native 给软件研发带来了哪些工程变化。读者读完以后应当能够区分代码补全、对话式编程和受控 Agent 执行，也能理解后续为什么还要建设 Agent Harness、运行环境、安全与可观测。

## 读者

文章面向已经使用过 AI 编辑器或编程 Agent 的开发者。默认读者理解代码仓库、测试、权限和发布流程，不要求提前了解 Agent 平台架构。

## 内容主线

文章从一个常见研发任务进入。同一句“把登录接口加上限流”，交给聊天模型、代码助手和工程 Agent 时，系统承担的工作范围并不相同。

正文沿着四个变化展开。

1. 开发者需要把任务、约束与验收条件说清楚。
2. 仓库规则、文档、历史状态和工具结果成为运行上下文。
3. Agent 需要在生成以后执行测试与检查，验证结果重新进入下一轮判断。
4. 企业需要提供身份权限、隔离环境、安全限制与完整 Trace。

文章结尾说明边界。高风险写操作仍由确定性服务和人工审批控制，Agent 负责在授权范围内组织步骤。后续文章再分别展开 Harness、运行环境、安全和可观测。

## 配图

正文使用一张 Mermaid 流程图，展示任务进入 Agent 后怎样经过上下文装配、工具执行、验证和结果交付。再用一张对照表比较传统自动化、AI 辅助编码与 AI Native 研发。

## 写作边界

文章不复述厂商案例，不把产品宣传作为结论，也不虚构作者亲历。公开手册只用于核对主题范围，正文用通用工程场景解释选择与风险。栏目首页删除原有的调研声明，只保留简短定位和已完成文章入口。
