# Agent 评测与服务安全文章设计

## 背景

现有 AI Agent 学习路线把日志、链路追踪、测试集、评测、权限、成本、并发和部署集中在工程化阶段。Agent 进入真实业务以后，版本验证和服务安全承担的职责不同，需要分别说明。

第一篇文章从一次线上问题修复出发，解释为什么单个案例复现成功不能证明整个 Agent 版本变好，并给出任务级评测、业务状态校验、新旧版本对比和回归集维护的方法。

第二篇文章以公开的模型蒸馏防御案例为起点，讨论 Agent 服务怎样保护系统提示词、Skill、内部上下文、知识内容和工具能力。文章需要区分基础模型服务商与普通 Agent 应用的责任，避免把所有异常调用都称为蒸馏攻击。

## 目录归属

两篇文章放入 `agent-learning-path/`，保持扁平目录。

```text
agent-learning-path/
├── README.md
├── agent-evaluation.md
└── agent-service-security.md
```

学习路线调整为五个阶段。

1. 大模型应用基础
2. 知识与工具
3. Agent 系统
4. 可观测性与评测
5. 生产治理与安全

## Agent 评测文章

拟用标题为《Agent 评测怎样判断一次修改有没有真的变好》。

文章回答下面的问题。

- 为什么修复一个失败案例仍然可能让其他任务退化
- Trace、最终回复、工具调用和业务最终状态分别能证明什么
- 怎样把线上问题整理成可重复执行的评测案例
- 怎样恢复一致的业务初始状态并比较新旧版本
- 哪些结果适合代码检查、人工判断或模型评分
- 怎样隔离调优案例与独立评测案例
- 怎样把线上确认问题沉淀为固定回归集

文章包含一张从线上反馈到发布门禁的流程图，并使用订单处理示例说明过程证据与任务结果的差别。

## Agent 服务安全文章

拟用标题为《Agent 服务怎样防止能力被批量提取》。

文章回答下面的问题。

- 合法模型蒸馏、未授权能力提取、普通爬取和业务滥用有什么区别
- 为什么单次请求检测不足以发现跨账号和跨时间的协同行为
- Agent 产品真正需要保护哪些资产
- 请求级检测与账号、组织级风险聚合怎样配合
- 内部上下文、Skill 和工具状态怎样保持完整性与访问隔离
- 怎样执行观察、限流、加强验证、阻断和封禁
- 攻击样本与误报样本怎样进入安全评测集
- 使用第三方模型与自建模型服务时各自承担什么责任

文章包含一张分层防御流程图。公开案例只用于说明工程选择和权衡，不复述具体攻击提示词，也不把公开指标写成项目实测结果。

## 两篇文章的关系

Agent 评测文章解决版本变化后的能力验证。服务安全文章解决生产环境中的持续滥用和能力保护。线上确认的失败、攻击和误报都可以进入评测数据，但进入固定回归集之前需要经过复核。

两篇文章互相链接，并链接到 `enterprise-ai-platform/data-foundation/data-feedback-evaluation.md`，复用现有的数据反馈、审核、数据集版本和发布门禁方法。

## 内容边界

- 不写入任职公司、客户、内部系统和真实业务数据
- 不照搬来源文章中的市场热度与未经外部验证的效果判断
- 公开数据只作为来源方案例，并在正文附近标明出处
- 优先使用业务最终状态做确定性判断，语义评分只承担适合它的部分
- 安全文章不提供可直接复现的推理提取或绕过步骤
- 普通 Agent 应用不能宣称能够控制第三方基础模型的内部推理

## 验收标准

- `agent-learning-path/README.md` 能清楚展示五阶段学习顺序和两篇文章入口
- 每篇文章只解决一个主要问题，读者可以独立阅读
- Mermaid 图在 GitHub Markdown 中语法完整
- 相对链接存在且方向正确
- 正文通过仓库写作检查，不出现公司内部信息和虚构效果数字
