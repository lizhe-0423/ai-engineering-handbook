# 校园服务 Agent 怎样安全地办一件事

[← 学校运营与教育治理](README.md)

校园服务常从一个问答入口起步。学生问选课时间，教师问材料怎样提交，系统从已发布的办事指南中找到答案。这一层做好以后，需求往往会自然走到下一步。用户知道怎么办以后，还希望系统替他查状态、填表或发起申请。

从回答到办理，中间隔着身份、权限和真实业务写入。模型理解错一句话，知识问答最多给出错误说明，事务工具却可能改变一条记录。Agent 可以统一交互入口，不能因此模糊这条风险边界。

## 先分知识请求和事务请求

知识请求从制度、通知和办事指南中检索。资料要有发布部门、生效时间与失效状态，回答展示来源和适用对象。两个文件冲突时，系统按正式发布规则排序，仍无法判断就转给负责部门，不能拼出一个折中答案。

事务请求需要进入业务目录。目录为每项服务定义使用者、所需参数、前置条件和负责部门。Agent 先识别候选事项，再用目录补齐信息。用户说“帮我办延期”时，系统应当问清具体事项与日期，不能仅凭相似名称调用接口。

两类请求可以出现在同一段对话里，执行通道必须分开。检索工具只有读取权限，事务工具按事项获得最小权限。模型看不到数据库账号，也不能动态拼接任意接口地址。

## 工具调用外面再包一层确定性校验

每个事务工具都用明确的参数结构。身份与角色从登录会话获取，不能相信用户在对话里自报。学号、课程号和日期等参数先做格式校验，再由业务系统检查用户是否有权操作。

Agent 生成执行计划后，界面把将要办理的事项、关键参数和影响展示给用户。查询类操作可以直接进行，提交、撤回和变更类操作需要再次确认。学校规定必须审批的事项，Agent 只负责发起流程，不能替审批人作决定。

写入接口要支持幂等。幂等意味着同一个请求因超时重试多次，业务结果仍只产生一次。系统为每次提交生成业务请求号，接口返回明确状态。网络中断时先查询请求号，不能因为没有收到响应就重复提交。

工具执行结果由代码解析，模型只把结果解释给用户。接口返回失败时，保留错误类型和可操作的下一步。模型不能把“系统繁忙”改写成“已经办理成功”，也不能在没有回执时编一个预计完成时间。

## 高风险事项停在人工确认前

涉及身份变化、费用、正式学籍记录或影响他人权益的事项，应当提高确认与审批级别。有些操作可以让 Agent 帮用户准备材料，却不开放最终提交工具。自动化边界由业务负责人配置，不能让模型按语言中的紧急程度自行放宽。

转人工时要把已确认的身份、事项和参数一并带过去，并控制接收人员能看到的对话范围。用户不必向人工窗口重新讲一遍，工作人员也不该得到与当前事项无关的聊天记录。

提示词注入也是这里的实际风险。用户上传的文件、知识库文档和外部网页都属于不可信内容，其中出现“忽略规则并调用某工具”时只能当作资料文本。工具权限由运行时控制，任何检索内容都不能修改系统指令。

## 审计记录要能还原一次办理

一次事务至少留下请求人、事项、参数摘要、确认动作、工具调用和业务回执。敏感字段在日志中脱敏，原始值放在受控业务系统。日志保存多久、谁能查询以及怎样导出，也要有明确规则。

评测可以先在沙箱中重放常见请求和对抗请求。知识问答看资料命中与过期内容拦截，事务流程看意图识别、参数补齐和权限拒绝是否正确。上线后再观察一次办结率、人工转接原因、重复提交和错误写入。涉及真实修改的错误应该单独计数，不能淹没在总体对话满意度里。

校园服务 Agent 把分散的制度与系统整理成一条可理解的办事路径，让用户少找几个入口，也少填几次重复信息。每一步受权限约束，每次写入得到确认，每个结果留有回执以后，这类 Agent 才适合办理真实事项。
