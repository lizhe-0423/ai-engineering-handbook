# 子代理怎样接受委派并返回结果

[← AI Agent 学习路线](README.md)

主 Agent 正在整理周报，用户又要求核对某项任务的阻塞原因。主 Agent 可以自己查询，也可以把这项范围明确的工作委派给子代理。子代理完成以后，主 Agent 仍要检查结果并决定怎样纳入最终交付。

子代理是由主代理或运行时启动、处理子任务的 Agent 执行单元。它可以使用独立上下文，也可以接收父任务的部分上下文。本文使用虚构的只读查询说明边界。

## 委派时要说清楚什么

一个可检查的子任务至少包括目标、输入、允许使用的能力、输出要求和时间预算。

```text
目标：核对 TASK-1002 当前阻塞原因
允许行动：读取当前用户有权访问的任务状态和阻塞记录
输出：已确认的状态、原因、来源；缺失时说明未确认
限制：不得修改任务，不得发送消息
```

这份文字只是任务约定，权限不能由它自己授予。运行时应为子代理配置真实的工具范围，任务服务仍要验证用户对具体资源的权限。

## 新上下文和继承上下文

新上下文只接收主任务显式传入的材料，适合研究独立问题，也更容易控制信息范围。代价是主代理必须把必要条件讲清楚，否则子代理可能不知道当前项目、时间范围或用户授权。

继承上下文可以减少重复描述，但会复制无关历史、过期结论或敏感内容。即使产品提供 fork 等机制，也要按实际实现确认复制了什么。复制上下文不等于继承更多工具权限。

对周报核查，可以只传任务编号、时间范围、问题和允许工具，不必把整段用户对话或其他任务的数据全部交给子代理。

## 返回的是结果，不是自动生效的决定

子代理可以返回状态、证据、未确认项和错误。例如它查到 `TASK-1002` 受阻，但原因查询超时，就应分别报告已确认的状态与未确认的原因。主代理检查编号、来源和时间后，再决定是否继续查询或告知用户。

子代理说“已发送周报”，不能单凭这句话认定发送成功。涉及外部副作用时要核对工具返回的操作标识和业务状态。主代理与子代理各自生成的调用标识也不能替代业务幂等键。

## 控制并发和取消

多个子任务可并行时，需要限制数量、总时限与共享工具的并发。两个子代理同时修改同一文件可能互相覆盖，应划定写入范围、串行合并或检查版本冲突。

主任务被取消时，运行时应向子代理发出取消请求并停止接受新的子任务。取消可能与外部请求同时发生，已经提交的写操作仍要对账。子代理超时后的结果即使后来到达，也需要按任务版本检查，避免覆盖更新后的主任务。

## 什么时候委派有价值

委派适合需要隔离上下文、控制权限或并行处理的子问题。一次简单的任务查询未必值得启动额外 Agent；启动、传递上下文和复核本身也消耗时间。

验证时检查子任务是否获得足够但不过量的材料、是否使用允许的工具、失败时是否诚实返回缺失项，以及取消后是否继续发生新操作。多个角色怎样分工见[多 Agent 协作](multi-agent-collaboration.md)，跨服务传递任务则见 [A2A](a2a-agent-cooperation.md)。
